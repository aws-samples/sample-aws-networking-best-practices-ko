# 변경 이력 {#changelog}

결정에 영향을 미치는 콘텐츠 변경 사항을 여기에 기록합니다. 최신 항목이 먼저 표시되며 풀 리퀘스트가 병합된 월별로 그룹화됩니다. 첫 번째 항목은 2026년 7월부터 시작합니다. 오타 수정, 깨진 링크 수정, 서식, CI, 사이트 메타데이터 변경은 목록에 포함되지 않습니다. 해당 내용은 [커밋 이력](https://github.com/aws/aws-networking-best-practices/commits/main)에서 확인할 수 있습니다. 이 페이지를 통해 마지막으로 읽은 이후 권장 사항이 변경되었는지, 또는 이전 학습 데이터를 기반으로 답변하는 AI 모델이 현재 지침을 반영하고 있는지 확인하세요.

**포함 기준:** 이전 버전의 페이지를 적용한 독자가 이제 다른 결정을 내리게 될 경우 해당 항목을 여기에 포함합니다.

| 아이콘 | 유형 | 사용 시점 |
| --- | --- | --- |
| 🆕 | 새로운 지침 | 새로운 모범 사례, 섹션 또는 서비스 기능이 문서화된 경우 |
| 🔄 | 변경된 권장 사항 | 이전과 다른 조언 또는 기본 선택이 제시된 경우 |
| 🔧 | 수정 | 독자의 행동에 영향을 미치는 방식으로 사실적·기술적 오류 또는 다이어그램 오류가 수정된 경우 |
| 🗑️ | 제거됨 | 지침, 권장 사항 또는 섹션이 폐기된 경우 |

## 2026년 11월 {#november-2026}

* 🆕 **새로운 가이드** — [AWS 내 연결](connectivity/within-aws.md#enable-cloud-wan-flow-logs-from-day-one), [내부 트래픽 모니터링](observability/internal-traffic.md#transit-gateway-and-cloud-wan-flow-logs-for-cross-vpc-visibility): AWS Cloud WAN Flow Logs를 사용하면 네트워킹 계정에서 코어 네트워크를 통과하는 트래픽을 단일 뷰로 확인할 수 있습니다. 코어 네트워크를 배포할 때 Flow Logs를 활성화하고, 바이트를 합산하기 전에 `flow-direction`으로 필터링하세요. 각 흐름은 트래픽이 진입하는 지점과 진출하는 지점 모두에서 기록되기 때문입니다. Cloud WAN은 터널리스 Connect 또는 Transit Gateway 라우팅 테이블 어태치먼트의 흐름을 기록하지 않으므로, 피어링을 통한 마이그레이션 중에는 Transit Gateway Flow Logs를 계속 실행하세요. ([#215](https://github.com/aws/aws-networking-best-practices/pull/215))
* 🔧 **수정** — [AWS 내 연결](connectivity/within-aws.md#apply-routing-policies-at-network-boundaries), [하이브리드 및 멀티 클라우드](connectivity/hybrid-multicloud.md#use-bgp-attributes-for-traffic-engineering-across-multiple-direct-connect-paths): 이전 가이드에서는 BGP 커뮤니티가 VPN 및 Connect 어태치먼트에서는 동작하지만 Direct Connect 어태치먼트에서는 동작하지 않는다고 설명했습니다. 이제 커뮤니티는 Site-to-Site VPN, Connect, Direct Connect 어태치먼트에서 동작하지만, Transit Gateway 라우팅 테이블 어태치먼트에서는 동작하지 않습니다. Direct Connect를 통해 경로를 태깅할 때는 자체 ASN을 사용하세요. `7224:*` 커뮤니티는 Cloud WAN에 도달하지 않고, 두 위치에서 동일한 프리픽스를 광고할 경우 최적 경로의 커뮤니티만 유지되며, 요약된 경로는 커뮤니티 없이 온프레미스로 반환됩니다. ([#215](https://github.com/aws/aws-networking-best-practices/pull/215))

* 🆕 **새로운 가이드** — [네트워크 성능 모니터링](observability/network-performance.md#network-health-indicator): Network Synthetic Monitor, Network Flow Monitor, Internet Monitor 중 선택하는 방법과, 네트워크 상태 지표(network health indicator)를 사용하여 경로 성능 저하를 AWS 네트워크에 귀인하는 방법에 대한 새로운 가이드가 추가되었습니다. ([#213](https://github.com/aws/aws-networking-best-practices/pull/213))
* 🔄 **권장 사항 변경** — [하이브리드 및 멀티 클라우드](connectivity/hybrid-multicloud.md#use-aws-interconnect-last-mile-where-your-network-provider-supports-it): 이전에는 며칠 내에 연결이 필요한 경우 Site-to-Site VPN만 안내했고, Direct Connect가 유일한 프라이빗 온프레미스 옵션이었습니다. 이제 사이트가 해당 메트로의 지원 공급자에 이미 연결되어 있는 경우 AWS Interconnect - last mile이 권장되는 관리형 프라이빗 경로이며, 그 외 지역에서는 Direct Connect가 기본 옵션입니다. ([#208](https://github.com/aws/aws-networking-best-practices/pull/208))
* 🆕 **새로운 가이드** — [인터넷 연결](connectivity/internet.md#external-security-provider-egress): AWS 네이티브 이그레스의 대안으로 외부 SASE(Secure Access Service Edge) 또는 프록시 공급자를 통한 라우팅 이그레스가 추가되었습니다. 이 가이드에서는 인터넷 바운드 트래픽을 위한 전용 리전 라우팅 도메인, 공급자에게 각 리전의 반환 프리픽스만 광고하는 방법, 소스 주소 유지와 소스 NAT 적용 간의 트레이드오프, 그리고 복원력, 모니터링 및 IPv6 설계를 다룹니다. ([#203](https://github.com/aws/aws-networking-best-practices/pull/203))
* 🔄 **권장 사항 변경** — [하이브리드 및 멀티 클라우드 연결](connectivity/hybrid-multicloud.md#private-on-premises-connectivity-with-aws-direct-connect), [AWS 서비스 모니터링](observability/service-monitoring.md#direct-connect): 이전 Direct Connect 가이드는 위치 복원력, BFD, 운영 지표를 별도로 다루었으나, LAG 장애 경계, 장애 상태 용량, 게이트웨이 용량 경계, 또는 서비스 시작 전 프리픽스 할당에 대한 설명이 없었습니다. 이제 이러한 사항들은 하나의 통합된 설계로 구성됩니다: 디바이스 및 위치 전반에 걸친 독립적인 경로, 충분한 생존 용량, 라우팅 및 할당 경계에 맞춰 정렬된 게이트웨이, 그리고 마이그레이션 전에 계획 및 모니터링되는 프리픽스 용량. ([#202](https://github.com/aws/aws-networking-best-practices/pull/202))
* 🆕 **새로운 가이드** — [AWS 내 연결](connectivity/within-aws.md#build-segmentation-with-purpose-specific-route-tables), [AWS 서비스 모니터링](observability/service-monitoring.md#monitor-quotas-before-you-hit-them): Transit Gateway에서 기본 연결, 기본 전파, 공유 어태치먼트의 자동 수락을 비활성화하고, 실패 시 차단(fail closed) 방식의 중앙 자동화를 통해 어태치먼트를 분류하세요. 라우팅 정책은 기본 경로 전파를 제어하고, 서비스 삽입은 트래픽을 검사 경로로 유도합니다. 할당량 모니터링은 이제 모든 Transit Gateway 라우팅 테이블의 총 경로 수, 각 Connect 피어와 교환되는 경로 수, Direct Connect BGP 프리픽스 수를 추적합니다. ([#201](https://github.com/aws/aws-networking-best-practices/pull/201))
* 🔄 **권장 사항 변경** — [CIDR 계획](foundation/cidr.md#allocate-contiguously-for-route-summarization), [AWS IPAM](foundation/ipam.md#design-pools-top-down-organization-region-environment-workload), [Amazon VPC](foundation/vpc.md#enable-dual-stack-from-day-one-on-new-vpcs), [AWS 사전 요구 사항](foundation/aws-prerequisites.md#ipv6-readiness): 이전에는 IPv6 경로 요약을 별도로 다루었고, BYOIP를 조직 전체 소스의 유일한 옵션으로 제시했으며, `/56` VPC 및 `/64` 서브넷 할당을 규정했습니다. 이제 IPv4와 IPv6는 하나의 연속된 계층 구조를 사용하고, 프라이빗 ULA/GUA는 조직 전체의 내부 전용 주소 지정을 지원하며, IPAM 할당 규칙은 계층 구조와 성장에 맞게 VPC 및 서브넷 프리픽스 크기를 조정합니다. ([#200](https://github.com/aws/aws-networking-best-practices/pull/200))
* 🆕 **새로운 가이드** — [하이브리드 및 멀티 클라우드 연결](connectivity/hybrid-multicloud.md#multi-cloud-connectivity): 클라우드 간 연결을 선택하거나 크기를 결정하기 전에 애플리케이션 및 데이터 배치를 먼저 결정하세요. 빈번하게 통신하는 계층은 동일한 클라우드에 유지하고, 반복적으로 읽는 데이터가 있는 곳으로 컴퓨팅을 이동하며, 워크로드가 사용하는 객체만 전송하고, 일회성 대량 이동에는 임시 용량을 사용한 후 남은 트래픽을 기준으로 링크 크기를 결정하세요. ([#204](https://github.com/aws/aws-networking-best-practices/pull/204))
* 🔧 **수정** — [AWS IPAM](foundation/ipam.md#ipam-pricing-and-cost-considerations): 이전에는 프라이빗 주소 거버넌스에 IPAM이 사실상 무료라고 설명했습니다. 이제 해당 페이지에서 권장하는 조직 전체 기능은 Advanced Tier가 필요하며, 활성 IP 주소(프라이빗 또는 퍼블릭)당 요금이 청구된다고 명시합니다. 또한 비용 범위를 제한하는 방법으로 OU 제외, 운영 리전 제한, 비용 배분 사용을 안내합니다. ([#199](https://github.com/aws/aws-networking-best-practices/pull/199))

## 2026년 10월 {#october-2026}

* 🔧 **수정** — [CIDR 계획](foundation/cidr.md#plan-for-hybrid-connectivity-from-day-one): 하이브리드 연결 단락에서 CIDR 중복이 항상 재-IP 작업을 요구한다는 내용을 수정했습니다. 이제 재-IP 작업 또는 하이브리드 경로에서의 영구적인 주소 변환을 두 가지 비용이 많이 드는 해결 방법으로 명시합니다. ([#185](https://github.com/aws/aws-networking-best-practices/pull/185))
* 🔧 **수정** — [CIDR 계획](foundation/cidr.md#never-overlap-cidr-blocks-across-vpcs-you-might-connect), [IPAM](foundation/ipam.md), [기반](foundation/index.md#5-ip-address-planning-with-cidr-blocks), [컨테이너 메시](application-networking/container-mesh.md#when-amazon-vpc-lattices-model-doesnt-fit), [AWS 내 연결](connectivity/within-aws.md#migrating-from-transit-gateway): CIDR 중복 시 Transit Gateway 또는 AWS Cloud WAN을 통한 연결이 불가능하며 VPC 재생성이 유일한 네트워크 수준의 해결책이라고 기술한 내용을 수정했습니다. 비중복 할당이 여전히 권장 사항이며, 관리형 1:1 NAT는 기존 지침을 수정하거나 변경하는 경우에만 문서화됩니다. ([#183](https://github.com/aws/aws-networking-best-practices/pull/183))
* 🆕 **새로운 지침** — [아웃바운드 제어](security/outbound.md#prefer-domain-based-filtering-over-ip-based-filtering-for-outbound-controls): Network Firewall 도메인 필터링이 이제 비-TLS 프로토콜을 지원하며, VPC에 연결된 DNS Firewall 규칙 그룹을 사용하는 Resolved IP Validation을 통해 SNI/Host 스푸핑에 대한 저항성을 갖출 수 있습니다. ([#182](https://github.com/aws/aws-networking-best-practices/pull/182))
* 🆕 **새로운 지침** — [경계 제어](security/perimeter-inbound.md#choose-between-centralized-and-per-vpc-inspection-deliberately): AWS Cloud WAN 서비스 삽입은 AWS Transit Gateway를 통해 공유 검사 VPC로 트래픽을 라우팅하는 방법과 함께, 중앙 집중식 검사 VPC로 트래픽을 라우팅하는 두 번째 방법입니다. AWS Firewall Manager는 중앙 집중식 검사에서 선택 사항입니다. Firewall Manager를 통한 VPC별 검사는 VPC가 많은 환경에서 기본값으로 유지됩니다. ([#166](https://github.com/aws/aws-networking-best-practices/pull/166))
* 🔧 **수정** — [경계 제어](security/perimeter-inbound.md#use-stateless-rules-for-high-volume-simple-filtering-and-stateful-rules-for-protocol-aware-inspection): 이전에는 스테이트리스 및 스테이트풀 규칙 분리가 비용 절감 수단으로 제시되었습니다. 이제 AWS Network Firewall은 어떤 규칙 엔진이 트래픽을 평가하든 관계없이 엔드포인트 시간 및 처리된 기가바이트에 대해 요금을 부과하므로, 이 분리는 처리 비용을 줄이는 방법이 아닌 규칙 설계 선택 사항임을 명시합니다. ([#166](https://github.com/aws/aws-networking-best-practices/pull/166))
* 🆕 **새로운 지침** — [로드 밸런싱](application-networking/load-balancing.md#manage-flow-lifetime-and-failure-recovery): Gateway Load Balancer는 대상이 비정상 상태가 되거나, 등록 해제되거나, 플로우가 유휴 상태로 만료될 때 TCP 리셋을 전송할 수 있으므로, 송신자는 TCP 재시도가 만료될 때까지 기다리는 대신 새 플로우를 열 수 있습니다. 기존 로드 밸런서를 포함한 세 가지 설정 모두 기본적으로 비활성화되어 있으며, 5-튜플 플로우 고정성이 필요합니다. TCP 유휴 타임아웃을 350초 이상으로 높일 경우, 대상의 연결 추적 유휴 타임아웃을 Gateway Load Balancer 값 이상으로 유지하십시오. ([#167](https://github.com/aws/aws-networking-best-practices/pull/167))
* 🆕 **새로운 지침** — [DNS 아키텍처](foundation/dns.md#turn-dns-query-logs-and-dns-firewall-activity-into-metrics-and-alarms): Amazon Route 53 Resolver 쿼리 로그를 Amazon CloudWatch Logs로 전달하여 지표 필터 및 알람을 구성하고, DNS Firewall 쿼리 볼륨 지표에 대해 직접 알람을 설정하십시오. 쿼리 로그는 캐시된 조회, DNS-over-HTTPS, 하드코딩된 IP 트래픽을 누락하므로, 이를 예방이 아닌 탐지 수단으로 활용하십시오. ([#175](https://github.com/aws/aws-networking-best-practices/pull/175))
* 🆕 **새로운 지침** — [아웃바운드 제어](security/outbound.md#scope-egress-rules-to-container-workloads): Network Firewall 컨테이너 연결은 Amazon ECS 태스크 및 Amazon EKS 파드를 동적 소스 IP 집합으로 추적하므로, VPC를 공유하는 워크로드에 서로 다른 이그레스 규칙을 적용할 수 있습니다. Amazon EKS VPC CNI에서 소스 NAT가 활성화된 상태로 남아 있는 등 충족되지 않은 제약 조건이 있으면 규칙이 자동으로 일치하지 않을 수 있습니다. ([#176](https://github.com/aws/aws-networking-best-practices/pull/176))
* 🆕 **새로운 지침** — [AWS 내 연결](connectivity/within-aws.md#account-for-the-tunnel-endpoint-when-planning-a-cidr-range-configuration): Amazon VPC Lattice VPC 리소스는 호스트를 사전에 알 수 없는 세그먼트에 대해 GENEVE 캡슐화를 사용하는 터널 엔드포인트를 통해 도달하는 CIDR 범위를 나타낼 수 있습니다. CIDR 범위 구성은 NAT를 수행하지 않고, 서비스 네트워크에 참여할 수 없으며, 사용자 지정 도메인 이름이 없으므로, CIDR 중복 이점은 단일, 그룹 및 ARN 구성에만 적용됩니다. ([#174](https://github.com/aws/aws-networking-best-practices/pull/174))
* 🔄 **권장 사항 변경** — [원격 액세스](connectivity/remote-access.md#aws-client-vpn): 이전에는 SSH 및 RDP 액세스가 AWS Client VPN을 선택하는 이유로 나열되었으며, AWS Verified Access는 VPN 클라이언트가 필요 없다고 설명되었습니다. 이제 특정 애플리케이션에 대한 TCP, SSH, RDP 액세스는 Verified Access에 적합하며(비-HTTP(S) 엔드포인트는 Connectivity Client가 필요), Client VPN은 다수의 호스트 및 포트에 대한 임시 액세스, 비-TCP 프로토콜, IP 기반 레거시 애플리케이션에 적합합니다. ([#173](https://github.com/aws/aws-networking-best-practices/pull/173))
* 🆕 **새로운 지침** — [원격 액세스](connectivity/remote-access.md#combine-identity-with-device-posture): Client VPN은 사용자 ID 외에 디바이스 포스처를 요구할 수 있으며, 연결 시점에 확인되고 세션 기간 동안 재평가됩니다. 포스처 게이트 엔드포인트는 AWS 제공 클라이언트만 허용하므로, 적용하기 전에 디바이스 신뢰 공급자 적용 범위를 확인하고 섀도우 모드에서 정책을 실행하십시오.
