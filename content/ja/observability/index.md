# オブザーバビリティ {#observability}

このセクションでは、AWS ネットワークへの可視性を確保する方法について説明します。具体的には、どのようなトラフィックが流れているか、そのトラフィックを運ぶサービスが正常に動作しているか、そして問題が発生した際に通知を受け取る方法です。ネットワークのオブザーバビリティは単一のダッシュボードではなく、各データソースが異なる問いに答える多層的なアプローチであり、それらを組み合わせることで全体像を把握できます。

オブザーバビリティは、接続性・アプリケーションネットワーキング・セキュリティの各レイヤーの上に成り立っています。それらのレイヤーが生成するログ、メトリクス、イベントを収集し、実用的なインサイトへと変換します。オブザーバビリティがなければ、接続障害のトラブルシューティング、セキュリティインシデントの検出、コストの帰属、そしてアーキテクチャが設計通りに動作しているかの検証ができず、盲目的な運用を強いられます。

## 1. 内部トラフィックモニタリング {#1-internal-traffic-monitoring}

**内部トラフィックモニタリング**は、AWS 環境内のリソース間 — VPC 間、サブネット間、ENI 間 — のトラフィックフローへの可視性を提供します。これはネットワークセキュリティ分析、コスト帰属、および接続トラブルシューティングの基盤となります。

**主なデータソース:**

*   **VPC Flow Logs** — VPC、サブネット、または ENI レベルでのパケットレベルのメタデータ。40 以上のカスタムフォーマットフィールドに対応
*   **Transit Gateway Flow Logs** — 単一の設定から VPC 間・アカウント間のトラフィックを一元的に可視化
*   **VPC Lattice アクセスログ** — アイデンティティ、レイテンシー、認証の判断を含むリクエスト単位のサービス間詳細情報
*   **Network Firewall ログ** — ルール帰属を含むステートフルインスペクションの判断結果(許可、拒否、アラート)
*   **Amazon Athena** — S3 に保存された Flow Logs を大規模分析するための SQL ベースのクエリ

***重要なインサイト:*** *VPC Flow Logs は本番環境でオプションではありません。アプリケーションログに相当するネットワークの記録であり、これがなければセキュリティインシデントの調査、接続問題のトラブルシューティング、実際のトラフィックパターンの把握ができません。*

## 2. 外部トラフィックモニタリング {#2-external-traffic-monitoring}

**外部トラフィックモニタリング**は、AWS 環境とパブリックインターネットの境界を越えるトラフィック — クライアントからの受信と外部サービスへの送信の両方 — への可視性をカバーします。各レイヤーは他のレイヤーでは捉えられない情報を記録します。

**主なデータソース:**

*   **CloudFront アクセスログ / リアルタイムログ** — エッジレベルのクライアント体験(レイテンシー、キャッシュステータス、プロトコル、地理的分布)
*   **ALB / NLB アクセスログ** — リクエスト単位またはコネクション単位の詳細情報(ターゲットレイテンシー、レスポンスコード、TLS メタデータ)
*   **AWS WAF ログ** — セキュリティ評価結果(ルールマッチ、許可/ブロックの判断、リクエスト属性)
*   **NAT ゲートウェイの CloudWatch メトリクス** — 送信ボリューム、コネクション数、ポート枯渇、パケットドロップ
*   **Route 53 クエリログ** — パブリックホストゾーンの DNS クエリパターン

***重要なインサイト:*** *ALB アクセスログは生成が無料で、保存コストも数セント程度であり、インシデント調査において代替不可能です。本番 ALB でこれを無効にしておく正当な理由はありません。*

## 3. AWS サービスモニタリング {#3-aws-services-monitoring}

**AWS サービスモニタリング**は、ネットワーキングサービス自体の運用上の健全性に焦点を当てます — トラフィックの流れではなく、そのトラフィックを運ぶインフラが正常かどうかです。ブラックホールドロップが発生している Transit Gateway、ポート割り当てを使い果たしている NAT ゲートウェイ、フラッピングしている Direct Connect 接続は、トラフィックモニタリングだけでは検出できないサービスレベルの障害です。

**主なパターン:**

*   **サービスごとの重要メトリクス** — Transit Gateway、NAT ゲートウェイ、Direct Connect、VPN、ALB、NLB、Network Firewall、VPC Lattice の実際の運用上の問題を示す特定の CloudWatch メトリクス
*   **コンポジットアラーム** — 複数のシグナルを組み合わせて実際の問題を確認してからページングすることで、アラート疲れを軽減
*   **異常検出** — 手動でのしきい値調整なしにトラフィックパターンに適応する ML ベースのアラート
*   **クォータモニタリング** — サービス制限に達する前に 80% 使用率でアラームを設定
*   **一元化されたダッシュボード** — ネットワーキングチーム向けのクロスアカウント・クロスリージョンの可視性

***重要なインサイト:*** *CloudWatch メトリクスはサービスが正常であることを示します。合成ヘルスチェックはパスがエンドツーエンドで機能していることを示します。両方が必要です — ルーティングが壊れた正常なサービスでも、障害は発生します。*

## 4. 通知 {#4-notifications}

**通知**は、問題の検出と適切な担当者への対応依頼の間のギャップを埋めます。モニタリングにおける最大の運用上の失敗はアラート疲れです — 誤検知や優先度の低いノイズが多すぎるためにチームがアラートを無視するようになることです。

**主なサービス:**

*   **CloudWatch アラーム** — しきい値、異常検出、コンポジットアラームを使用したメトリクスベースのアラート
*   **Amazon EventBridge** — 状態変化(VPN トンネルのダウン、Direct Connect のフラッピング、BGP セッションの切断)に対するイベント駆動型通知
*   **Amazon SNS** — メール、PagerDuty、Lambda、SQS へのファンアウト配信
*   **AWS Health Dashboard** — お客様のリソースに影響する AWS サービスイベントのプロアクティブな把握
*   **AWS Chatbot** — インタラクティブなアクションを備えた Slack および Microsoft Teams へのアラーム配信

***重要なインサイト:*** *チームが日常的にアラームを無視しているなら、モニタリングの問題ではなくアラーム設計の問題です。すべてのアラームには明確なオーナーと定義された対応アクションが必要です。*
