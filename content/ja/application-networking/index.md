# アプリケーションネットワーキング {#application-networking}

このセクションでは、アプリケーショントラフィックの分散方法、サービスの検出と相互通信の方法、およびコンテナワークロードにおけるサービス間接続の管理方法について説明します。アプリケーションネットワーキングは接続レイヤーの上位に位置し、その基盤となるインフラストラクチャ(VPC、サブネット、IP アドレッシング)を利用します。

ここで取り上げるアプリケーションネットワーキングサービスは、「VPC 間でルーティングできる」状態と「アプリケーションコードが呼び出しを行う」状態の間に存在する課題、すなわちサービス間通信における負荷分散、サービスディスカバリ、認証、トラフィック管理、およびオブザーバビリティを担います。

## 1. ロードバランシング {#1-load-balancing}

**Elastic Load Balancing** は複数のターゲットにトラフィックを分散することで、アプリケーションの可用性を維持し、水平スケーリングを可能にし、個々のターゲット障害を吸収します。AWS は 3 種類のマネージドロードバランサーを提供していますが、これらは互換性がありません。それぞれ異なるトラフィッククラスとアーキテクチャ上の役割に対応して設計されています。

**主要サービス:**

*   **Application Load Balancer (ALB)** — HTTP、HTTPS、gRPC 向けの L7 ロードバランシング。コンテンツベースルーティング、TLS ターミネーション、相互 TLS、AWS WAF 統合に対応
*   **Network Load Balancer (NLB)** — TCP、UDP、TLS、QUIC 向けの L4 ロードバランシング。超高スループット、クライアント IP 保持、アベイラビリティゾーンごとの静的 IP に対応
*   **Gateway Load Balancer (GWLB)** — サードパーティ製ネットワークアプライアンス(ファイアウォール、IDS/IPS)をデータパスに透過的に挿入。ALB および NLB とは構造的に異なる

***重要なポイント:*** *ALB と NLB はアプリケーショントラフィックをターゲットに分散します。GWLB は根本的に異なる役割を担います。サードパーティ製アプライアンスのフリートをデータパスに透過的に挿入するものです。GWLB を ALB や NLB と同列に扱うことが、最も多い混乱の原因です。*

## 2. サービス間通信 {#2-service-to-service}

**サービス間通信**は、あらゆる本格的なアプリケーションの結合組織です。重要な問いは「ALB か NLB か?」ではなく、「コンシューマーはどのようにプロバイダーを見つけるか?」「サービス同士はどのように認証し合うか?」「ターゲットに障害が発生したらどうなるか?」「新バージョンを安全にデプロイするにはどうすればよいか?」といったものです。

**主要パターン:**

*   **サービスディスカバリ** — Route 53 プライベートホストゾーン、AWS Cloud Map、Amazon VPC Lattice DNS
*   **認証と認可** — SigV4 を使用した Amazon VPC Lattice 認証ポリシー、セキュリティグループ、相互 TLS
*   **トラフィック管理** — Amazon VPC Lattice の重み付きルーティング、ALB の重み付きターゲットグループ、Route 53 の重み付きレコード
*   **クロス VPC およびクロスアカウントアクセス** — Amazon VPC Lattice サービスネットワーク、AWS PrivateLink エンドポイントサービス、既存接続上の内部ロードバランサー
*   **非同期パターン** — プライベート API への直接接続を使用した Amazon EventBridge および AWS Step Functions

***重要なポイント:*** *各パターンは個別のビルディングブロック(Route 53、PrivateLink、ALB、IAM)を組み合わせてチームが統合を担う形で構築することも、Amazon VPC Lattice を通じてカバーすることもできます。VPC Lattice はディスカバリ、認証、クロス VPC 到達性、トラフィック管理、オブザーバビリティを単一のマネージドレイヤーに統合します。*

## 3. コンテナメッシュ {#3-container-mesh}

**コンテナメッシュ**は、コンテナ化されたワークロードがサービス間通信を処理する方法を扱います。クラスター内プリミティブからクラスター間接続、フルサービスメッシュのデプロイまでを対象とします。重要な問いは「どの具体的な機能が必要か、そしてそれぞれをどこに配置すべきか?」です。

**主要パターン:**

*   **クラスター内コンテナネットワーキング** — Amazon VPC CNI、Pod Identity、ポッド向けセキュリティグループ、ECS サービスコネクト、awsvpc ネットワークモード
*   **メッシュの代替としての Amazon VPC Lattice** — メッシュコントロールプレーンを使わずに、AWS Gateway API Controller を通じたクラスター間・クロス VPC・クロスアカウントのサービス通信
*   **セルフマネージドサービスメッシュ** — サイドカーメッシュ機能が真に必要な場合に、Amazon VPC Lattice または従来の AWS 接続の上で Istio、Cilium、Linkerd を実行

***重要なポイント:*** *サービスメッシュを採用する目的のほとんどは、AWS マネージドサービスによってすでにネイティブにカバーされています。セルフマネージドメッシュを採用するのは、特定のサイドカーメッシュ機能(メッシュ管理の mTLS ライフサイクル、メッシュ CRD、リクエスト単位のレジリエンスポリシー)が真の要件である場合に限定してください。*
