# 新しいベストプラクティスの提案 {#propose-a-new-best-practice}

AWS ネットワーキングのガイダンス改善に関するアイデアをお持ちですか？ぜひお聞かせください！このページでは、コミュニティ全体に役立つ新しいベストプラクティスを提案する手順をご説明します。

## 概要 {#quick-overview}

提案を送信する前に、以下をご確認ください。

1. **本当に新しいベストプラクティスかどうかを確認する**（[バグ報告]ではないか）

2. **既存のソリューションを調査**し、参照する

3. **AWS re:Post でコミュニティと議論**する

4. **テンプレートを使用して詳細な提案を送信**する

準備ができましたか？完全なプロセスについては、引き続きお読みください。

  [バグ報告]: report-a-correction.md

## 良い提案の条件 {#what-makes-a-good-proposal}

### 本当に新しいベストプラクティスですか？ {#is-this-really-a-new-best-practice}

新しいベストプラクティスは、コミュニティに大きな価値をもたらすものである必要があります。次の点を自問してください。

* これは一般的なネットワーキングの課題を解決しますか？

* 自組織だけでなく、複数の組織に役立ちますか？

* これはネットワーキング固有のガイダンスですか（一般的な AWS アドバイスではなく）？

**迷っている場合：** エラーや不整合を報告する場合は、代わりに[修正報告](report-a-correction.md)をご利用ください。

### 調査を行う {#do-your-research}

* AWS ドキュメント、ブログ、フォーラムで既存のソリューションを検索する

* 既存のガイダンスを参照し、提案がどのように改善するかを説明する

* 関連トピックについて[コミュニティディスカッション](https://repost.aws/topics/TA-2izgznkTKe0-VdIELPAgg/networking-content-delivery)を確認する

[:octicons-comment-discussion-16:&nbsp; ディスカッションに参加する][AWS re:Post Networking & Content Delivery community]{ .md-button .md-button--primary }

  [AWS re:Post Networking & Content Delivery community]: https://repost.aws/topics/TA-2izgznkTKe0-VdIELPAgg/networking-content-delivery

## Issue テンプレート {#issue-template}

提案を送信する準備ができましたか？必要な情報をすべて含めるために、[このテンプレート](https://github.com/aws/aws-networking-best-practices/issues/new?template=new-best-practice.md)をご使用ください。

* タイトル
* コンテキスト <small>任意</small>
* 説明
* 関連リンク
* ユースケース
* ビジュアル <small>任意</small>

### タイトル {#title}

良いタイトルは短く、内容を的確に表しています。アイデアの概要を一文で表したものにしてください。タイトルだけで、コミュニティへの潜在的な影響と利点が伝わるようにします。

| <!-- --> | 例  |
| -------- | -------- |
| :material-check:{ style="color: #4DB6AC" } **明確** | SD-WAN integration with TGW |
| :material-close:{ style="color: #EF5350" } **冗長** | Add a feature where you describe how to integrate various SD-WAN options with a Transit Gateway |
| :material-close:{ style="color: #EF5350" } **不明確** | Improve TGW |
| :material-close:{ style="color: #EF5350" } **無意味** | Help |

### コンテキスト <small>任意</small> { #context }

アイデアを説明する前に、達成しようとしていることを理解するための追加コンテキストを提供できます。提案するベストプラクティスを使用する状況と、関連すると_思われる_内容を説明してください。ここでは実際のベストプラクティスについては記述しないでください。

> **これが役立つ理由**: アイデアによっては、特定のお客様、環境、またはエッジケース（例：ネットワークに数千の VPC が含まれる場合）にのみ利点をもたらすものがあります。コンテキストを少し提供することで、ベストプラクティスガイドの優先順位をより正確に決定できます。

### 説明 {#description}

次に、アイデアの詳細かつ明確な説明を提供してください。なぜそのアイデアが AWS ネットワーキングアーキテクチャガイドに関連し、他の AWS ドキュメントやブログ記事ではなくここに追加すべきなのかを説明してください。

*   **<u>何を</u>するかを説明し、<u>なぜ</u>するかは説明しない** – ここではアイデアの

    利点を説明する必要はありません。それは後で行います。
    提案するソリューションをできる限り正確に説明することに集中してください。

*   **簡潔にまとめる** – アイデアを説明する際は、要点を絞って簡潔に

    記述してください。過度に詳しく説明する必要はありません。メンテナーや将来のユーザーは、読む量が少ない方が助かります。

*   **一度に一つのアイデア** – 関連性のない複数のアイデアがある場合は、

    それぞれについて別々の新しいベストプラクティス提案を作成してください。

---

> **これが必要な理由**: 提案された変更を理解・評価するために、アイデアを明確に把握する必要があります。詳細かつ正確な説明を提供することで、コメント欄でのさらなる説明のやり取りに費やす時間を節約できます。

### 関連リンク {#related-links}

新しいベストプラクティス提案に関連する Issue、ディスカッション、またはドキュメントセクションへの関連リンクを提供してください。このアイデアについてディスカッションボードでコミュニティと既に議論している場合は、そのディスカッションへのリンクも含めてください。

> **これが必要な理由**: 関連リンクは、追加のコンテキストを提供することで、新しいベストプラクティス提案の包括的な理解を深めるのに役立ちます。また、過去の Issue やディスカッションへのリンクを含めることで、コミュニティからすでに提供されたフィードバックや意見を迅速に評価できます。

### ユースケース {#use-cases}

新しいベストプラクティス提案がユーザーの視点からどのように機能するかを説明してください。期待される影響は何か、なぜあなただけでなく他のユーザーにも利益をもたらすのか、そしてどれくらいの数のユーザーに影響するかを説明してください。さらに、他のベストプラクティスを壊す可能性はありますか？

> **これが必要な理由**: アイデアのユースケースと利点を理解することは、プロジェクトとそのユーザーへの潜在的な影響と有用性を評価する上で非常に重要です。この情報により、アイデアの期待される価値と、プロジェクトの目標との整合性を理解できます。

### ビジュアル <small>任意</small> { #visuals }

ここまでで、潜在的なユースケースや関連リンクを含む、アイデアの明確で詳細な説明が揃いました。スケッチ、スクリーンショット、モックアップ、外部アセットなどのビジュアルがある場合は、このセクションで提示してください。

**ファイルをここにドラッグ＆ドロップするか、外部アセットへのリンクを含めてください。**

また、この変更、機能、または改善が他の公開 Web サイトで使用されているのを見たことがある場合は、その例を示し、どのように実装・組み込まれているかを説明してください。

> **これが役立つ理由**: イラストやビジュアルは、メンテナーがアイデアをより深く理解し、具体的にイメージするのに役立ちます。スケッチや図は、テキストだけでは伝えられない詳細さと明確さをもたらします。また、他の公開 Web サイトでアイデアがどのようにドキュメント化されているかを確認することで、その潜在的な影響と実現可能性を理解し、新しいベストプラクティス提案の評価とトリアージに役立てることができます。

**あとはこちらで対応します。**

## 提案送信後 {#after-you-submit}

提案を送信したら：

* **辛抱強く待つ** – コミュニティへの影響を検討するため、レビューには時間がかかります

* **ディスカッションに参加する** – 質問やフィードバックに回答する

* **変更を受け入れる姿勢を持つ** – コミュニティの意見を通じてアイデアが発展する可能性があります

* **関与し続ける** – 承認された提案の実装を支援することを検討する

## 提案が却下された場合 {#if-your-proposal-is-rejected}

却下は残念なことだと理解しています。提案は以下の基準に基づいて評価されます。

* コミュニティへの利益と広い適用可能性

* プロジェクトの目標との整合性

* 実装とメンテナンスの労力

* 明確さと完全性
