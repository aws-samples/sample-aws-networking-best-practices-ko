# コントリビューション {#contributing}

AWS Networking Best Practices Guide へようこそ！本プロジェクトはコミュニティ主導で運営されており、あなたのようなユーザーからのコントリビューションによって成り立っています。問題の報告、改善の提案、専門知識の共有など、どのような形でも、このガイドをより良いものにするためのご協力をお待ちしています。

## コントリビューションが初めての方へ {#new-to-contributing}

まずは以下のよくある方法からお試しください。

!!! tip "クイックスタートガイド"

    **誤りや情報の不足を見つけた場合** → [修正を報告する](report-a-correction.md)

    **ネットワーキングに関する質問がある場合** → [AWS re:Post で質問する](https://repost.aws/questions/ask)

    **新しいベストプラクティスを提案したい場合** → [新しいベストプラクティスをリクエストする](new-best-practice.md)

    **コンテンツのコントリビューションを行う準備ができた場合** → [プルリクエストを作成する](making-a-pull-request.md)

多くのコントリビューションは、問題の報告や質問から始まります。完璧でなくても大丈夫です。コミュニティがサポートします！

## コントリビューションガイドライン {#contribution-guidelines}

コントリビューションをできる限り簡単に行えるよう、プロセスを整理しています。以下のシンプルなガイドラインに従うことで、コントリビューションへの対応を迅速かつ効果的に行うことができます。

## チェックリスト {#checklist}

プロジェクトに関わる前に、以下の点について少し考えてみてください。これにより、適切な Issue テンプレートを使用しているか、またコミュニティとのやり取りに必要な情報をすべて提供しているかを確認できます。

## 良いコントリビューションと悪いコントリビューション {#good-vs-poor-contributions}

### ✅ 良い例 {#good-examples}

**ドキュメントのギャップ**: 「ネットワーキング基礎セクションには、マルチリージョン展開における CIDR ブロック計画に関するガイダンスが不足しています。小規模 (VPC 数 10 未満) および大規模 (VPC 数 50 超) の組織向けの例を含む、IP アドレス割り当て戦略に関するベストプラクティスセクションをコントリビューションしたいと思います。」

**コンテンツの拡充**: 「現在の AWS 内接続セクションは基本的なセットアップをカバーしていますが、高度なルーティングシナリオが不足しています。具体的な例と図を含む、ハブアンドスポークアーキテクチャ向けのルートテーブル設計パターンに関するセクションを追加できます。」

**新しいベストプラクティス**: 「本番環境での AWS Network Firewall の使用経験に基づき、コスト考慮事項とモニタリング戦略を含む、ルールの最適化とパフォーマンスチューニングに関するセクションをコントリビューションしたいと思います。」

### ❌ 悪い例 {#poor-examples}

**曖昧なリクエスト**: 「ネットワーキングについてもっと情報が必要」

**範囲が広すぎる**: 「ドキュメントをすべて修正してください」

**コンテキストなし**: 「セキュリティグループについて何か追加してください」

!!! note "コミュニティガイドライン"
    すべてのコントリビューションは公開され、永続的に残ります。建設的かつ敬意を持った態度で、[行動規範](https://aws.github.io/code-of-conduct)に従ってください。

## コントリビューション前の確認事項 {#before-you-contribute}

コントリビューションが有益なものとなり、適切に対応されるよう、以下のチェックリストをご確認ください。

* **まず検索する**: 同じ問題がすでに報告されていないか、または類似の質問がないかを確認する

* **適切なチャネルを使用する**:

  * 技術的な質問 → [AWS re:Post](https://repost.aws/questions/ask)

  * バグ報告や機能リクエスト → [GitHub Issues](https://github.com/aws/aws-networking-best-practices/issues)

* **コンテキストを提供する**: AWS サービス、リージョン、エラーメッセージなど関連する詳細情報を含める

* **敬意を持って接する**: [行動規範](https://aws.github.io/code-of-conduct)に従い、議論を建設的に保つ

!!! info "ご注意"
    Issue テンプレートを完全に記入することで、リクエストの内容をより迅速に把握できます。不明な点があっても心配しないでください。コミュニティがサポートします！

## 権利と責任 {#rights-and-responsibilities}

メンテナーとして、私たちはコミュニティ内のコミュニケーションを管理する**責任**を担っています。これには、コントリビューションガイドラインおよび[行動規範](https://aws.github.io/code-of-conduct)に**沿わない**ユーザーに対して、Issue、ディスカッション、コメント、コミットのクローズ、削除、却下、編集、およびユーザーのブロックを行う権限が含まれます。

この役割を果たすために、コミュニティの健全性と良好な雰囲気を維持することに積極的に関与する必要があります。これらの基準を毅然とした態度で守ることで、すべてのメンバーにとって敬意ある包括的な環境を確保します。

### 行動規範 {#code-of-conduct}

[行動規範](https://aws.github.io/code-of-conduct)は、すべてのコミュニティメンバーが互いに敬意を持って接し、包括的で歓迎的な言葉を使用することへの期待を定めています。私たちは、不適切、攻撃的、または有害な行動のない、ポジティブでサポーティブな環境を育むことを約束します。

違反行為は真剣に受け止め、これらの価値観を守るために適切な措置を講じます。[^1]

  [^1]:
    **警告およびブロックポリシー:**
    プロジェクトの人気の高まりと健全なコミュニティへのコミットメントを踏まえ、違反への対応方針を明確に定めました。

    1.1. **最初の警告:** 不適切、攻撃的、または有害な行動を繰り返すユーザーには最初の警告を行います。この警告は、その行動がコミュニティ基準および行動規範に沿っていないことを正式に通知するものです。最初の警告は永続的に記録されます。

    1.2. **2 回目の警告と解決の機会:** 行動が改善されない場合、2 回目の警告を行います。2 回目の警告を受けたユーザーには、5 日間の反省期間が与えられます。この期間中、ユーザーは自身の行動について公に説明または謝罪することが推奨されます。この期間は、誤解を公に解消する機会を提供することを目的としています。

    1.3. **ブロック:** 2 回目の警告後も応答がなく、行動の改善も見られない場合、コミュニティおよびリポジトリからユーザーをブロックする権利を留保します。ブロックはあくまで最終手段であり、コミュニティの健全性と良好な雰囲気を守るために絶対に必要な場合にのみ使用します。

    ブロックは、私たちの非常にポジティブなコミュニティにおいて極めてまれな措置であり、建設的な対話と相互尊重を優先する姿勢を示しています。これはコミュニティメンバーとチームを守ることを目的としています。

### 不完全な Issue と重複 {#incomplete-issues-and-duplicates}

私たちは、Issue を効果的にレビューし対応するための要件を評価できるよう、コントリビューションプロセスの整備に多大な時間と労力を投じてきました。Issue テンプレートの各フィールドは、お客様の懸念事項と問題の性質を十分に理解するために慎重に設計されています。重複を避けるため、新しい Issue を提出したりディスカッションを開始したりする前に、検索機能を活用されることをお勧めします。コミュニティのディスカッションを建設的かつ整理された状態に保つために、皆様のご協力が不可欠です。

  * **Issue テンプレートの必須記入:** Issue テンプレートに必要なすべての情報を記入していただく必要があります。これにより、経験の有無にかかわらず、すべてのユーザーとメンテナーがバグ報告や変更リクエストの内容と重大度を理解できるようになります。

  * **不完全な Issue のクローズ:**

  品質基準や Issue テンプレートの要件に従っていないものなど、*必要な情報が不足している Issue をクローズする権利を留保します*。不足している情報が提供された場合、そのような Issue は再オープンできます。

  * **重複の処理:** [Issue トラッカー]内のコミュニケーションを整理し効率的に維持するため、*重複した Issue をクローズする権利を留保します*。同じ質問をしたり、同じ問題を異なるフォーラムで複数報告したりすることは、コミュニティの懸念事項を管理・対応する能力を妨げます。重複した質問は複数のチームメンバーの時間を同時に消費するため、効率的な時間管理の観点からも重要です。各 Issue やディスカッションが固有であり、新しい情報とともに進展することを確保することで、集中力を維持しコミュニティをサポートできます。

    さらに、*新しい情報を提供せずに再オープンされた Issue、または単にユーザーが Issue や質問への回答をまだ受け取っていないという理由で再オープンされた Issue を即座にクローズする権利を留保します*。当該 Issue は不完全としてマークされます。

  * **自動化ツールの制限:** Lighthouse、アクセシビリティツールなどの自動化ツールが潜在的な問題の特定にもたらす価値と効率性を認めていますが、これらのツールによって生成された Issue を単に提出するだけでは、完全なバグ報告とはなりません。これらのツールは冗長な出力を生成することがあり、誤検知を含む場合もあるため、批判的な評価が必要です。もちろん、生成されたレポートを Issue に添付することは歓迎します。ただし、これは最小限の再現手順や調査結果の詳細な議論の要件に代わるものではありません。*これらの Issue を不完全としてマークし、クローズする権利を留保します。* この方針により、広範な自動化出力を精査するのではなく、真の懸念事項に対して正確かつ明確に対応できます。
