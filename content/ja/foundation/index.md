# 基盤 {#foundation}

このセクションでは、AWS ネットワーキングの基本的な構成要素について説明します。接続性、アプリケーションネットワーキング、セキュリティ、または可観測性のソリューションを実装する前に、これらのコアコンセプトを理解することが不可欠です。このガイドの残りのすべてのサービスとパターンは、ここで説明する基盤の上に構築されています。

基盤レイヤーは「どのようにリソースを接続するか」という問いの前に来る問いに答えます。組織はどのように構成されているか、ネットワークはどこに存在するか、どのアドレス空間を使用するか、そのアドレス空間はどのように管理されているか。これらの決定を正しく行うことで、その上のすべてがクリーンに機能します。誤った決定は、後から修正するのにコストがかかる制約を生み出します。

## 1. 始める前に {#1-before-you-start}

すべての VPC、ルートテーブル、および Transit Gateway アタッチメントはアカウント内に存在し、IAM ポリシーによって管理され、サービスクォータの対象となり、コードを通じてデプロイされる必要があります。単一の CIDR ブロックに触れる前にこれらの非ネットワーキング基盤を正しく整えることで、後から修正が最も困難な問題を防ぐことができます。

**主なトピック:**

*   **Identity and Access Management (IAM)** — クロスアカウントロール、サービスリンクロール、SCP、およびネットワークリソースの条件キー
*   **Infrastructure as Code** — ネットワークリソース管理のための CloudFormation、Terraform、および CDK
*   **サービスクォータ** — デプロイを制限するクォータと、その計画的な対処
*   **タグ付け戦略** — コスト配分、自動化ターゲティング、およびポリシー適用
*   **Well-Architected Framework** — ネットワーキングに適用されるセキュリティ、信頼性、コスト最適化の柱

## 2. AWS Organizations とアカウント構造 {#2-aws-organizations-and-account-structure}

**AWS Organizations** は、ネットワークリソースの共有方法、セキュリティ境界の適用方法、およびチームが接続の混乱を生じさせることなく独立して運用する方法を決定するガバナンスレイヤーです。Organizations がなければ、すべてのクロスアカウントネットワーキングパターンは、スケールしない手動の信頼関係を必要とします。

**主なコンセプト:**

*   **組織単位 (OU)** — RAM 共有、SCP 適用、およびアタッチメント自動化のスコープを定義する論理グループ
*   **サービスコントロールポリシー (SCP)** — セキュリティだけでなく、ネットワークアーキテクチャを適用するガードレール
*   **集中型ネットワーキングアカウント** — Transit Gateway、Direct Connect、Route 53 Resolver、および IPAM 専用のアカウント
*   **RAM によるリソース共有** — 自動継承のために OU レベルでネットワーキングリソースを共有

***ベストプラクティス:*** *ワークロードアカウントより前に専用のネットワーキングアカウントを確立してください。後続のすべてのアカウントは共有ネットワーキングリソースに依存することになり、集中型ネットワーキングを後から導入することは、最初から集中型で始めるよりも大幅に困難です。*

## 3. Amazon VPC {#3-amazon-vpc}

**Amazon Virtual Private Cloud (VPC)** は、基盤となるセキュリティ境界、IP アドレスドメイン、およびその上のすべてのネットワーキング決定を形成するルーティングコンテキストです。ネットワーク接続を必要とするすべてのコンピューティングリソース、データベース、コンテナ、および Lambda 関数は VPC 内で実行されます。

**主な決定事項:**

*   **VPC 設計パターン** — ワークロードごとの VPC (最も一般的)、RAM による共有 VPC (集中管理)、またはアカウントごとのマルチ VPC
*   **CIDR サイジング** — 本番環境では `/16` から始め、`/20` より小さくしない
*   **IPv6 の採用** — 新しい VPC ではデュアルスタックを最初から有効化
*   **Flow Logs** — 包括的なセキュリティとトラブルシューティングの可視性のために VPC レベルで有効化

***ベストプラクティス:*** *すべてにカスタム VPC を使用してください。デフォルト VPC は削除するか無視してください。組織全体のデフォルト VPC でのリソース作成を拒否する SCP をデプロイしてください。*

## 4. リージョンとアベイラビリティーゾーン {#4-regions-and-availability-zones}

**AWS リージョン**は、完全に独立したインフラストラクチャを持つ別々の地理的エリアです。各リージョンには複数の**アベイラビリティーゾーン (Availability Zones)** が含まれており、低レイテンシーのプライベートファイバーで接続された物理的に分離されたデータセンターです。デプロイするすべてのネットワーキングリソースは正確に 1 つのアベイラビリティーゾーンに存在し、マルチ AZ 戦略が耐障害性、コスト、および影響範囲を決定します。

**主な考慮事項:**

*   **リージョン選択** — レイテンシー、Direct Connect の場所、サービスの可用性、コンプライアンス、およびコスト
*   **AZ ID と アベイラビリティーゾーン名** — アベイラビリティーゾーン名はアカウントごとにランダムにマッピングされます。クロスアカウントの調整には AZ ID を使用してください
*   **マルチ AZ パターン** — すべてのステートフルなネットワーキングリソースを AZ ごとにデプロイし、N-1 アベイラビリティーゾーンの容量でサイジング
*   **クロス AZ コスト** — 各方向で GB あたりの料金が発生します ([VPC 料金](https://aws.amazon.com/vpc/pricing/)を参照)。可用性を犠牲にすることなく不要なクロス AZ トラフィックを最小化してください

***ベストプラクティス:*** *本番ワークロードは少なくとも 3 つのアベイラビリティーゾーンにデプロイしてください。1 つのアベイラビリティーゾーンが失われても残りの 2 つに過負荷がかからないよう、AZ ごとの容量をサイジングしてください。*

## 5. CIDR ブロックによる IP アドレス計画 {#5-ip-address-planning-with-cidr-blocks}

**CIDR (Classless Inter-Domain Routing)** 表記は、VPC とサブネットの IP アドレス範囲を定義します。IP アドレス計画は、後から簡単に変更できない最も重要な初期決定事項です。すべての VPC、ピアリング接続、ハイブリッドリンク、およびルートテーブルは、作成時に選択した CIDR によって制約されます。

**主な原則:**

*   **連続的に割り当てる** — ルート集約を可能にし、ファイアウォールルールを簡素化し、トポロジーを読みやすくします
*   **重複させない** — CIDR が重複する VPC は、ピアリング、Transit Gateway、または Cloud WAN で接続できません
*   **ハイブリッドを計画する** — AWS への割り当てを行う前にオンプレミスの範囲と調整してください
*   **10.0.0.0/8 を使用する** — 最大の連続したプライベート空間で、深い階層的な割り当てをサポートします

***ベストプラクティス:*** *階層的な割り当てを設計してください: 組織 → 環境 → リージョン → VPC → サブネット。この構造により、すべてのレベルでルート集約が可能になり、ネットワークトポロジーが自己文書化されます。*

## 6. サブネット {#6-subnets}

**サブネット**は、ルーティングポリシーと IP アドレッシングが交わる場所です。起動するすべてのリソースはサブネットに配置され、そのサブネットのルートテーブルがリソースが到達できる場所を決定します。「パブリック」と「プライベート」はルートテーブルのプロパティであり、サブネット自体のプロパティではありません。

**主なパターン:**

*   **5 層アーキテクチャ** — ファイアウォール、パブリック、プライベート (アプリケーション)、データ、およびインフラストラクチャ/トランジットサブネット
*   **層ごとにアベイラビリティーゾーンごとに 1 つのサブネット** — すべてのアベイラビリティーゾーンで一貫性を保つ
*   **ワークロードに合わせてサイジング** — ほとんどの層では `/24`、EKS/ECS コンテナサブネットでは `/22` 以上
*   **インフラストラクチャサブネット** — Transit Gateway ENI、ファイアウォールエンドポイント、および VPC エンドポイント ENI 専用の `/28` サブネット

***ベストプラクティス:*** *サブネットスキームに番号のギャップを残してください (0、1、2、3 ではなく 0、10、20、30)。これにより、既存のサブネットを中断することなく後から新しい層を挿入できます。*

## 7. IP アドレス管理 (IPAM) {#7-ip-address-management-ipam}

**AWS IPAM** は、スプレッドシートと属人的な知識を、すべてのアカウントとリージョンにわたって IP アドレスを計画、割り当て、追跡、および監視する集中型のポリシー駆動システムに置き換えます。IPAM がなければ、IP アドレス管理は調整のボトルネックに陥り、VPC を接続しようとしたときにのみ発見される重複を生み出します。

**主な機能:**

*   **階層的プール** — 組織 → リージョン → 環境 → ワークロード、各レベルに割り当てルールを設定
*   **重複防止** — すべての割り当てがプール階層全体に対して検証される
*   **コンプライアンス監視** — 標準に違反する手動割り当て CIDR を持つ VPC の継続的な検出
*   **IaC 統合** — CloudFormation と Terraform がハードコードされた CIDR の代わりに IPAM プールを参照

***ベストプラクティス:*** *最初の本番 VPC を作成する前に IPAM を実装してください。単一の CIDR 重複 (修正には VPC の再作成が必要) のコストは、数年分の IPAM のコストを超えます。*

## 8. DNS アーキテクチャ {#8-dns-architecture}

**Amazon Route 53 Resolver** は、VPC 内から行われるすべての DNS クエリを処理します。プライベートホストゾーンへのクエリへの応答、オンプレミスドメインへのクエリの転送、およびパブリックインターネット名の解決を行います。マルチアカウント環境では、DNS の決定がサービスディスカバリー、ハイブリッド接続、およびセキュリティ体制に連鎖します。Route 53 Profiles は、DNS 設定 (プライベートホストゾーンの関連付け、転送ルール、DNS Firewall ルールグループ) を OU レベルで配布し、すべてのアカウントが自動的に一貫した名前解決を継承できるようにします。

**主な機能:**

*   **Route 53 Profiles** — OU 内のすべてのアカウントに DNS 設定をバンドルして共有し、新しいアカウントが自動的に継承
*   **プライベートホストゾーン** — 関連付けられた VPC にのみ表示される内部 DNS 名前空間。サービスディスカバリーの基盤
*   **Resolver エンドポイント** — ハイブリッド DNS のためのインバウンド (オンプレミスが AWS 名を解決) とアウトバウンド (AWS がオンプレミス名を解決)
*   **DNS Firewall** — 解決レイヤーでのドメインベースのフィルタリング。最も安価で広範なエグレス制御

***ベストプラクティス:*** *Route 53 Profiles を最初からデプロイしてください。これがなければ、マルチアカウントの DNS は時間とともにドリフトする脆弱なアカウントごとの自動化になります。これがあれば、DNS 設定は組織とともにスケールするファーストクラスの運用になります。*
